# Portfolio Plan

## Goal

Build a small, high-quality GitHub portfolio that provides credible technical evidence of Cloud Infrastructure Engineering capabilities. The portfolio will prioritize GCP while demonstrating transferable architecture, security, networking, governance, FinOps, reliability, and Infrastructure as Code practices.

## Portfolio model

Cases will belong to a shared, fictional enterprise universe when continuity strengthens the narrative. Real-world experience may inform scenarios, but no proprietary data or artifacts may be used.

Each case follows this narrative:

```text
Problem → Requirements → Architecture → Decisions → Implementation → Validation
→ Security → Governance → Costs → Trade-offs → Outcome
```

## Incremental delivery plan

| Phase | Focus | Deliverable |
| --- | --- | --- |
| 0 | Professional GitHub foundation | Profile strategy and reusable repository standards |
| 1 | Architecture design | Fictional scenario, requirements, diagrams, and ADRs |
| 2 | Cloud foundation | Resource hierarchy, project model, baseline policies, and logging design |
| 3 | Networking | VPC/Shared VPC, segmentation, routing, DNS, and hybrid design where justified |
| 4 | IAM and security | Access model, security controls, logging, and threat considerations |
| 5 | Governance | Naming, labels, policies, lifecycle, and operational guardrails |
| 6 | Infrastructure as Code | Terraform implementation and proportionate CI validation |
| 7 | Observability | Monitoring, alerting, logs, and operational signals |
| 8 | FinOps | Cost allocation, budgets, forecasts, and optimization opportunities |
| 9 | Reliability and DR | Availability, backup, RTO/RPO, and recovery design |
| 10 | Portfolio review | Recruiter-facing summary and technical documentation review |

## Current scope: Phase 0

The immediate objective is to make the GitHub presence coherent before building the GCP Landing Zone. This includes a profile README, naming conventions, documentation standards, commit and branch practices, issue and pull-request templates, labels, and reusable repository guidance.

The Landing Zone itself is explicitly out of scope until Phase 0 is complete and its fictional scenario is approved.

## Definition of done for every case

- The scope is tied to a plausible business requirement.
- All data and artifacts are fictional and safe to publish.
- The README explains the value, architecture, technologies, and evidence of skills quickly.
- Architecture decisions and trade-offs are documented where material.
- IaC and automation are present only when they serve the case.
- Applicable validation and repository-safety checks have passed.

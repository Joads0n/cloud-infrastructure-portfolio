# 0009: Single dev project, direct resources, and owner-operated Terraform

Status: Accepted. Supersedes the multi-environment workload target and module preference in ADRs 0007/0008. Historical seed ownership remains unchanged.

The dev deployment target is superseded by [ADR 0011](0011-single-production-project.md). The decision below records the earlier dev refactor, not current deployment instructions.

## Context

The owner confirmed using only the existing dev lab project and withdrew the preference for Google-maintained modules. The requested case still includes a global external LB, multiple backends, scaling, reserved IPs, firewall rules, and disk snapshots. Only seed has been applied; no workload state was found in the dev/prod roots during this refactor.

## Decision

Make `infra/environments/dev` the only active workload root. Use the Google provider directly, retaining one local workload module as a coherent implementation boundary, not a claim of cross-environment reuse. Remove internal-LB and prod branches from that module. Keep global LB resources under neutral `app` addresses, with two private replicas across two zones and bounded scaling to three.

The human operator uses ADC. Create one runtime service account in the dev root with no project roles/keys. API activation remains owned by existing seed. No prerequisite apply of legacy bootstrap, management buckets, provisioner accounts, or audit routing is required.

Use protected local state initially to avoid new bootstrap resources. This is an implementation choice for a single operator, not an assertion that local state is safer than GCS. Require restrictive permissions, encrypted storage, independent backups, and no concurrent execution. Remote state can be added later through a separately reviewed migration.

The owner executes every plan/apply/destroy and mock plan suite. The assistant may edit, format, statically validate, and review sanitized output. Disable the legacy controller's CLI, including watchdog mode, because its GCS/impersonation assumptions do not match this design. Cleanup is attended and manual; do not claim an automatic one-hour guarantee.

Retire prod's configuration as a non-executable `.tf.example`, with a warning. Preserve seed code/state and legacy unapplied bootstrap for history. Do not apply bootstrap alongside dev: both describe the runtime account name. No resource import, state migration, or cloud deletion accompanies these unapplied configuration changes.

## Alternatives Considered

- Preserve dev/prod and central management: unnecessarily broad for the agreed case.
- Require Google-maintained remote modules: explicitly withdrawn by the owner.
- GCS state plus a new administrative root now: useful for teams, but adds provisioning beyond this initial single-operator scenario.
- Reuse the former execution controller: unsafe without redesigning IAM, backend, resource checks, and watchdog responsibilities.

## Consequences

All historical saved workload/bootstrap plans are invalid for the new workflow and must not be executed. Old private input files must not be reused blindly. The project is supplied privately, never embedded in public Terraform. A fresh owner-generated plan must show only the dev workload and its runtime identity. Verify names, current state, ADC identity, permissions, quotas, exact image, and costs before apply.

Snapshots are outside workload state when generated by the policy. Manual cleanup includes exact snapshot/restore-disk targets, not only Terraform destruction. The BRL 300 portfolio ceiling, one-hour session with minute-40 teardown, and seed maintenance deadline remain unchanged. Retiring bootstrap access requires its own reviewed seed plan, not a side effect of this refactor.

## Trade-offs

The smaller scenario is easier to explain, but does not demonstrate environment isolation, org-wide governance, or team state collaboration. Human-run deployment and local state require explicit operational discipline. The local module preserves existing tested resource definitions while removing unused topology branches.
